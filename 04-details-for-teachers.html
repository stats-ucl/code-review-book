4  Details for Teachers

4.1 Detailed Process Walkthrough

4.1.1 GitHub Organization Setup

To create your one-time organization, follow the steps below:

  1. Go to https://github.com/settings/organizations
  2. Click “New organization”
  3. Choose organization name: UCL-[Department]-[Module]-[Year]
  4. Set to “Private” initially
  5. Add description and contact information

The codeinput package handles all repository creation and configuration.

4.1.2 Assessment Preparation

Before running automation, prepare:

Issue Templates (automatically created):

The create_github_templates() function uploads .github/ISSUE_TEMPLATE/peer-review.md and creates the peer-review issue label in each student repository, providing structured sections for:

  • Code quality assessment
  • Correctness evaluation
  • Constructive feedback
  • Learning reflections

Marking Criteria Integration:

If you are using a customized fork of the package, you can edit peer_review_template in create_github_templates() (R/github_functions.R) to align with your specific marking criteria:

# Customize the peer_review_template variable in create_github_templates()
# to match your assessment goals

Assignment Instructions:

Prepare clear instructions that reference:

  • Learning objectives for peer review
  • Timeline and deadlines
  • Technical support resources
  • Assessment weighting (if applicable)

4.1.3 Student Data Collection

Collect GitHub usernames at the start of the module.

Option 1 — Moodle Survey
Create a Moodle survey with:

  • “GitHub username” text field
  • Instructions for creating GitHub accounts
  • Link to GitHub Education benefits

Option 2 — Submission Requirement

Include GitHub username as part of the assignment submission requirements.

Option 3 — Lab Session Collection

Collect usernames during the first computer lab session.

4.1.4 File Transfer Workflow

Automated Process (Recommended):

# Run the main automation workflow (or source("main_automation_script.R"))
results <- run_automation(
  org_name = "UCL-StatSci-STAT0001-2025",
  assignment_name = "assignment-1",
  student_list_path = "student_list.csv",
  submissions_path = "submissions",
  output_dir = "output",
  reviews_per_student = 2,
  deadline = "2025-04-15",
  instructor_name = "Course Instructor"
)

Manual Process (Backup Method):

If automation fails, you can still upload files manually: 1. Create repositories individually 2. Upload files through GitHub web interface 3. Set permissions manually 4. Generate assignment lists manually

4.1.7 Troubleshooting with Automation

Common Issues and Solutions:

GitHub Authentication or Script Failures:

Ensure your GitHub PAT has the required scopes (repo, admin:org, user) and is stored via gitcreds or .Renviron:

library(codeinput)

# Check local configuration (token, student_list.csv, submissions/)
validate_configuration()

# Test GitHub API connection and organization access
test_github_connection("UCL-StatSci-STAT0001-2025")

Error Recovery (Idempotent Re-runs):

If run_automation() is interrupted midway: 1. Review the console output for specific error messages and resolve the underlying issue. 2. Re-run run_automation(). Repository creation (create_student_repo()), file uploads (put_repo_file()), issue label creation, and reviewer branch updates (create_reviewer_branches()) are all idempotent and will safely update or skip existing resources without failing.

Student Access Problems:

  • Verify GitHub usernames in student_list.csv (validate_student_data() checks for missing usernames and duplicate IDs)
  • Confirm that students have accepted the repository invitation sent by GitHub (set_reviewer_permissions() grants collaborator access to both the submitting author and their assigned reviewers)
  • Use check_repo_access(repo_name, username, org_name) to verify collaborator access for a specific student

File Upload Issues:

  • Check file sizes (GitHub API limit: 100MB per file)
  • Verify file paths in submissions/[student_id]/ folders
  • Review console output for specific error messages

Incomplete Reviews:

library(codeinput)

# Generate targeted reminders in output/reminders/ for reviewers with pending reviews
run_progress_check(
  org_name = "UCL-StatSci-STAT0001-2025",
  assignment_name = "assignment-1",
  output_dir = "output",
  deadline = "2025-04-15",
  instructor_name = "Course Instructor"
)

Security Considerations:

  • Never commit your GitHub token or student data to version control
  • run_setup() automatically creates a .gitignore that excludes .Renviron, student_list.csv, submissions/, and output/
  • Regularly rotate your GitHub Personal Access Tokens and remove collaborators who no longer need access

4.1.8 Advanced Features

Customizing Review Assignments:

Use parameters in run_automation() or call assign_peer_reviewers() directly:

library(codeinput)

# Change number of reviewers per student and set a random seed for reproducibility
assignments <- assign_peer_reviewers(
  students,
  reviews_per_student = 3,
  seed = 42
)

# Or pass directly to run_automation():
results <- run_automation(
  org_name = "UCL-StatSci-STAT0001-2025",
  assignment_name = "assignment-1",
  reviews_per_student = 3,
  seed = 42
)

assign_peer_reviewers() uses a balanced circular permutation design so that every student both gives and receives exactly reviews_per_student distinct reviews, with no self-reviews or duplicate reviewer pairs.

Integration with Continuous Assessment:

  • Use repository activity for participation grades
  • Track improvement over multiple assignments
  • Monitor collaborative discussion quality

Scaling for Large Classes:

The automation functions handle classes up to 200+ students efficiently: - Batch processing minimizes API rate limits - Progress monitoring scales automatically - Email generation (output/email_templates/email_merge_data.csv) handles large volumes

4.1.9 Alternative Workflows

For Smaller Classes (<20 students):

Consider having all students review all submissions for maximum learning.

For Advanced Students:

  • Enable pull request reviews in addition to issues (using the automatically created reviewer-1, reviewer-2, … branches)
  • Encourage code improvement suggestions
  • Allow collaborative debugging sessions

For Assessment-Heavy Modules:

  • Use multiple rounds of peer review
  • Implement peer review of peer reviews (meta-review)
  • Create portfolio-based assessment incorporating peer feedback

4.3 Resource Requirements

4.3.1 Technical Infrastructure

  • GitHub Organization: Free for educational use
  • codeinput R Package: Open-source, installed from GitHub
  • R/RStudio: Free, open-source software
  • Computing Resources: Minimal - runs on standard academic workstations

4.3.2 Time Investment

Initial Setup (First Time):

  • Package installation and setup (run_setup()): 30 minutes
  • GitHub organization setup: 15 minutes
  • Student data preparation: 45 minutes
  • Total: ~1.5 hours

Per Assignment (Ongoing):

  • File organization: 15 minutes
  • Running run_automation(): 5 minutes
  • Monitoring (run_progress_check()) and reminders: 10 minutes weekly
  • Total: ~20 minutes + weekly monitoring

4.3.3 Support Requirements

For Students:

  • Provide comprehensive student guide
  • Offer optional GitHub tutorial sessions
  • Establish peer mentoring system
  • Create backup support during lab sessions

For Teaching Staff:

  • Train additional instructors on codeinput package usage
  • Establish backup procedures for technical failures
  • Document customizations and local adaptations
  • Plan for software updates and maintenance

4.4 Success Metrics and Expectations

4.4.1 Short-term Indicators

  • >90% successful repository setup
  • >80% completion of peer reviews within deadline
  • <5% technical support requests requiring instructor intervention
  • Positive student feedback on learning experience

4.4.2 Long-term Outcomes

  • Improved code quality in subsequent assignments
  • Increased student confidence with collaborative tools
  • Enhanced peer learning culture in the module
  • Transferable skills development for industry preparation

4.5 Emergency Procedures and Backup Plans

GitHub Service Outages:

  • Monitor GitHub status page
  • Extend deadlines if necessary
  • Use manual review process as fallback
  • Communicate clearly with students

Script Failures:

  • Re-run run_automation() after resolving the error (functions are idempotent)
  • Use validate_configuration() and test_github_connection() to diagnose issues
  • Revert to manual repository creation if necessary
  • Document issues for future improvement

Student Technical Difficulties:

  • Provide alternative access methods
  • Offer individual technical support
  • Consider accommodation for accessibility needs
  • Maintain flexible deadline policies

Remember: The codeinput package handles the complex technical setup, allowing you to focus on the pedagogical aspects of peer review and student learning outcomes. Start small with one assignment, gather feedback, and iterate based on your experience and student needs.
