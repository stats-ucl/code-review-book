7  FAQs

7.1 For Students:

  1. How many reviews should I do, and who are going to review my work?
  • Reviews are assigned randomly; the exact number is defined by the course. Please follow the lecturer’s latest announcements for any special arrangements.
  1. I can’t open the repo or didn’t receive an invite. What should I do?
  • First, you should confirm that you have been enrolled on Moodle and added to the course’s GitHub organisation. If you are still unable to access the repo, please provide your name, student ID, and GitHub username/email, to the lecturer or teaching team.
  1. Why use GitHub for peer review?
  • GitHub provides private repositories, standardised issue templates, and an auditable history. This makes it easier to allocate tasks, keep reviewing evidence, and follow up. Becoming familiar with GitHub is also helpful for your future study and work.
  1. Can I comment on a single line or a specific code snippet?
  • Yes. In the file view, click the line number to get a URL with an anchor like #L42 or #L10-L20; paste that link into the Issue to point precisely. Press the y key on the file page to turn it into a permalink so it stays stable after edits. You can also paste a small snippet in the comment and briefly explain the context and suggestion.
  1. Do I need to run someone else’s code in my local environment?
  • Usually no——running untrusted code can be risky. If the template or course requires execution, use a safe, isolated environment (e.g., virtual environment or container), and follow the notes and sample data provided by the course. If you prefer not to run the code locally, you can use GitHub Codespaces in the browser. Always remember to follow safety guidance of your courses and avoid running suspicious scripts.
  1. I can’t see other students’ repos. Is that expected?
  • Yes. Repos are private by default and visible only to the author, assigned reviewers, and the teaching team.

7.2 For Lecturer:

  1. Can we start without having every student’s GitHub username?
  • Yes. We can directly invite students to the organisation or specific repos by email. They can accept with a GitHub account that has been verified, or sign up during acceptance.
  1. Students report “no access” or can’t open their repo, what should we check first?
  • Confirm that their GitHub username in student_list.csv is accurate and that they have accepted the repository invitation sent by GitHub (set_reviewer_permissions() grants collaborator access to both the submitting student and their assigned reviewers). You can verify collaborator status at any time using check_repo_access(repo_name, username, org_name).
  1. How do we control how many reviews each student gives or each submission receives?
  • Use the reviews_per_student parameter in run_automation() (or assign_peer_reviewers()), which assigns a balanced circular permutation so each student both gives and receives reviews_per_student distinct reviews. Before full rollout, a dry-run on a small roster is recommended to validate workload and connectivity. It is also recommended to announce this information to all students via email or on the Moodle page.
  1. Do we need anonymous peer review on GitHub?
  • By default, it is not anonymous because usernames are visible. If anonymity is required, use pseudonymous accounts or collect reviews via a separate form and post summaries back to the repo.
  1. After the deadline students keep pushing changes, what version is graded?
  • By default, grading is based on the version at the stated deadline. Later changes may remain for students to further learning, but they should not affect grading unless your course policy says otherwise.
  1. How do we monitor completion and chase late reviewers?
  • Run run_progress_check(), which queries Issues and Pull Requests across all student repositories, generates progress_check_[date].csv, student_progress_[date].csv, and reviewer_progress_[date].csv in output/, saves progress visualizations in output/progress_reports/, and creates targeted reminder emails in output/reminders/ for reviewers with incomplete reviews.
  1. Some students withdrew or never accepted invites, how do we fix lopsided assignments?
  • You should mark those students inactive and reassign only the edges touching them. Keep all other assignments intact to minimise churn.
  1. What naming and visibility scheme is recommended?
  • By default, run_automation() creates private repositories using the pattern student-{student_id}-{assignment_name} (e.g., student-12345-assignment-1). Personalized repository and reviewer branch links are automatically included in output/student_repo_links.csv and output/email_templates/.
